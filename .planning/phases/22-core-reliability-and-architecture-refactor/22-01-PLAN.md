# Plan 22-01: 地端 Agent 橋接佇列 SQL 分頁過濾、逾時回收機制與 CAS 條件更新（P1-1, P1-2）

## 任務目標
1. **CaseStore SQL 過濾支援（P1-1）**：
   - 在 `case_store/store.py` 為 `kind='bridge'` 提供專屬查詢方法 `list_bridge_jobs(status=None, s_type_code=None, limit=100, offset=0)`，直接在 SQLite 資料庫層以 `json_extract(payload, '$.status')` 或狀態欄位進行篩選。
   - `bridge_queue.py` 的 `list_pending()` 改用該查詢方法，取消在 Python 記憶體掃描 1000 筆的限制，徹底避免靜默丟件。

2. **SENDING 逾時回收機制（P1-2）**：
   - 任務由 `PENDING` 轉為 `SENDING` 時，記錄 `lease_started_at`（ISO 或時間戳）與 `lease_timeout_sec`（預設 900 秒 / 15 分鐘）。
   - 在 `list_pending()` 或回收排程中，偵測超逾租約時間仍處於 `SENDING` 的任務，自動將其回退為 `PENDING`，使其他或重啟後的地端 Agent 能重新認領。

3. **重試計數與最大限制（P1-2）**：
   - payload 增加 `retry_count`（預設 0）與 `max_retries`（預設 3）。
   - 當任務回報 `FAILED` 或逾時回收時，遞增 `retry_count`；若 `retry_count >= max_retries` 則標記為永久失敗（`FAILED_PERMANENT`），記錄原因不再重複派發。

4. **CAS 條件更新防範並發競態**：
   - `report_status()` 支援比對目前狀態（Compare-And-Swap），若預期狀態不符則拋出 `BridgeConflictError`（409），避免重複回報覆蓋。

5. **測試與驗證**：
   - 撰寫 `tests/test_bridge_queue_reliability.py`：
     - 測試 1500 筆以上任務時，第 1200 筆 `PENDING` 任務仍能被正確查出（驗證 P1-1）。
     - 測試 `SENDING` 逾時後自動回收重派（驗證 P1-2）。
     - 測試超過 `max_retries` 後停止重試。
     - 測試 CAS 競態防護。
