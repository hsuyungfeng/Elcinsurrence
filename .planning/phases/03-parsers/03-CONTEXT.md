# Phase 3: 解析器 - Context

**Gathered:** 2026-08-03
**Status:** Ready for planning

<domain>
## Phase Boundary

Phase 3 把三種輸入轉成下游可用的結構化 Python 物件：

1. **申報 XML**（`tdata`/`ddata`/`pdata`）→ 案件與醫令結構
2. **核減清單**（原送核補報樣本清單）→ 核減案件、核減醫令、申復值域上界
3. **SOAP 病歷文字** → S/O/A/P 四段定位

純資料轉換層：**無 LLM 呼叫、無外部服務依賴、無使用者可見輸出**。解析器不查規則庫、不判斷醫令是否存在、不做支持度判定——那些是 Phase 5 的職責。

</domain>

<decisions>
## Implementation Decisions

### 申報 XML 解析

- **D-01（編碼）:** 以 binary 讀檔，先讀 XML 宣告的 `encoding` 屬性，依序嘗試 `big5` → `cp950` → `big5hkscs` → `utf-8`，全部失敗才報錯。
  - **為何是硬性需求：** 真實檔 `TOTFA.xml` 宣告 `encoding="Big5"`，而 Python stdlib 的 `ElementTree` **無法直接解析 Big5**（拋 `ValueError: multi-byte encodings are not supported`）。必須先 decode 成 str 再餵給 parser。此限制在任何既有文件中都沒有記載。
  - 寬容回退的理由：不同 HIS 匯出可能是 `cp950`（Big5 超集，含更多異體字），病患姓名常有罕見字。

- **D-02（未知欄位全數保留）:** 解析器保留 XML 中出現的所有欄位；C11 未記載者收進 raw dict，不丟棄。

- **D-03（次診斷升為一級欄位）:** `d20`-`d26` 明確建模為「次診斷代碼清單」（ICD-10），不與其他未知欄位混在一起。
  - **理由：** 這些是 Phase 5 判斷「醫療必要性」的關鍵臨床佐證。`d20` 出現於 464/633 筆（73.3%），丟掉等於自斷一臂。C11 只列了 `d19` 主診斷。

- **D-04（CRLF）:** 真實檔為 CRLF 行尾，解析器不得假設 LF。

### 欄位缺漏分級（C5 的具體化）

- **D-05（致命，僅三種）:**
  1. 缺 `d1`/`d2` — 無法識別是哪一筆案件
  2. 缺 `d3` — 無法對應病歷
  3. 整筆案件沒有任何 `pdata` — 沒有醫令就沒有東西可比對

  **其餘一律可容忍。** 理由：本引擎的目的是盡量救回案件，不是把資料不完美的案子擋在門外。

- **D-06（d19 不列致命）:** 主診斷缺漏發警告但不拒收（真實檔 633 筆全數存在，實務極少觸發）。

- **D-07（回傳形狀）:** 解析整檔回傳單一 `ParseResult` 物件，內含：成功解析的案件清單 + 被拒收的案件（含拒收原因）+ 每案自帶的警告清單。
  - **理由：** 符合 C5「不阻斷整案」。633 筆中 1 筆壞掉不應停擺全部。呼叫端自行決定如何處理拒收案。

- **D-08（警告兩級）:** 只有高出現率欄位（>90%）缺席才發警告；低出現率欄位（<50%）視為「正常可空」不發警告。
  - **理由：** 避免 633 筆產生上千條雜訊警告，淹沒真正的異常。
  - 正常可空清單（真實出現率）：`d10` 18.6%、`d27` 50.9%、`d21` 37.3%、`d22` 19.0%、`p2` 47.1%、`p7`/`p9` 41.2%、`p14`/`p15` 29.8%、`p16` 7.1%、`p24` 5.0%
  - C5 說「缺 d10 → 警告繼續」獲真實資料佐證：d10 本來就只有 18.6% 出現率。

- **D-09（未知醫令不在此處理）:** 解析器只負責把 `p4` 醫令碼完整取出，**不呼叫 `get_rule()`、不判斷碼是否存在**。C5 的「入未知醫令清單」屬 Phase 5 職責。
  - **理由：** 保持解析器純粹——無外部依賴、可單獨測試、不需要 SQLite 檔就能跑、不提前綁死 Phase 2 介面。

### SOAP 分段

- **D-10（兩層策略）:** 先試標記偵測（正則，涵蓋 `S:`、`S)`、`【S】`、`主訴：` 等變體）；偵測不到才回退關鍵詞分類。

- **D-11（信度標記）:** 分段結果必須標明使用了哪種方法——marker-based（高信度）vs keyword-based（低信度），供 Phase 5 判斷該段分段可不可信。
  - **理由：** 已有標記的病歷分段是確定性的字串切割問題（準確率近 100%）；無標記文字是機率性分類問題（原分類器自稱 85-90%）。把兩者混為一談會讓下游誤信低品質分段。

- **D-12（移植關鍵詞、重寫演算法）:** 把 `officialdocument/soapclass/soap-classifier.js` 的 240+ 關鍵詞表移植成 Python 資料結構；分類邏輯用 Python 重寫。
  - **理由：** 關鍵詞表是累積的醫學詞彙資產，值得保留；演算法本身只有約 30 行實質邏輯（split → 計分 → argmax），不值得逐行移植。
  - **重寫時須修正：** 原版「無關鍵詞命中時預設歸類 subjective」的行為應改為「未分類」，避免無依據的猜測污染下游。

- **D-13（輸入介面）:** SOAP 來源為獨立文字檔（`.txt`/`.md`），符合 Phase 1 file-in/file-out 定位。

### 核減清單

- **D-14（依官方規格書建模）:** 依 `電子申復格式及填表說明門診.doc`（版本 104.02.11）的四段式結構建模：總表段（t）、清單段（d1-d7）、醫令段（p1-p9）、醫令統扣明細段。

- **D-14a（⚠️ 修正 D-14 的適用範圍——經文件查證）:** 上述規格書定義的是**申復「輸出」XML**，**不是核減「輸入」檔的格式**。本機**沒有任何一份文件定義核減輸入檔的欄位**。已窮盡查證：
  - `電子申復格式及填表說明門診.doc`、`門診申復上傳格式作業說明.doc` → 皆為**院所上傳**的申復 XML 規格（Big5，Phase 7 範疇）
  - `30396_*門診診療費用申復清單.odt/.pdf` → **空白三聯單樣張**，由「醫療院所依式詳填」後寄出，即申復 XML 的紙本前身（問答集 Q4：「即日起可以電子檔案方式辦理申復，**不必再填紙本申復清單**」）。其最右側「中央健康保險署填列」欄（審核意見／補付數量／單價／補付金額）由健保署回填後將第三聯送回院所——這是核減結果的**紙本**呈現位置。
  - 核減輸入的真正規格在 **VPN**：問答集 Q10 明載「請由 VPN 下載核減資料，另用 HELP 欄位說明了解，在『**核算資料醫令改支檔案下載欄位**』**第 9 欄**就是『改支序號』」；Q17 另指出「**醫令核減彙總表**」的核減代碼（e5）本署會提供電子檔，非樣本月與樣本月都會提供。
  - **因此核減至少有三個來源**：①核算資料醫令改支檔（定位欄位）②醫令核減彙總表 ③書面核減通知（問答集 Q1：「核減資料呈現於書面」）。
  - **對規劃的指示：** 三聯單欄位僅可作為**資料契約參考**（案件分類/流水號→`d1`/`d2`；醫令序→`p1`;理由→`p8`/`p9`；健保署填列區→核減值），**不得**據以撰寫欄位解析邏輯。

- **D-14b（Phase 3 範圍——使用者決定）:** 核減解析器**只定義介面，實作延後**。Phase 3 實交付**申報 XML parser + SOAP parser**（兩者皆有真實樣本可驗證）；核減部分僅產出 `DeductionRecord` dataclass 與 `load_deductions()` 契約，外加一個依規格造假資料的 adapter。取得真實 VPN 檔後只換 adapter，不動契約與下游。
  - **理由：** 沒有樣本就寫定位欄位解析＝猜欄位順序，猜錯要整個重寫；而 XML/SOAP 兩個解析器證據充分，不應被核減卡住。

- **D-15（核減值＝申復上界）:** 解析核減清單時**必須取出**核減點數／成數／數量，因為官方規格書硬性規定 `申復點數<=核減點數`、`申復成數<=核減成數`、`申復數量<=核減數量`。
  - **理由：** 核減清單不只是「被砍了什麼」的通知，它是申復值域的上界來源。不取出這些值，Phase 7 無法做合法性檢查。

- **D-16（樣本註記）:** `d3` 樣本註記需建模為列舉：`0`-統扣 / `1`-立意 / `2`-歸戶 / `3`-隨機 / `4`-全審。此註記決定哪些點數欄位必填。

- **D-17（整件核減用旗標）:** 整件核減（`d4`=Y）與逐醫令核減共用同一型別 `DeductionCase`，以 `whole_case_deducted` 布林旗標區分；整件核減時醫令清單可為空。
  - **理由：** 符合規格書「整件核減，整件申復，則醫令免申報」的語意；下游用旗標分流即可，不需維護兩套處理邏輯。

- **D-18（真實樣本——現況已更新）:** 核減真實樣本**目前無法取得**。使用者確認 VPN 可下載，但此規劃階段內拿不到樣本；本機亦無 HELP 欄位說明。規劃階段應：依 D-14b 只定契約＋造假資料 adapter，介面保留替換空間（沿用 `progress.md` 第 75 行既定策略）；真實樣本到手後補一輪驗證。
  - **取得樣本時要抓的兩份：**（1）核算資料醫令改支檔＋其 HELP 欄位說明（確認第 9 欄=改支序號的完整欄序）（2）醫令核減彙總表（核減代碼 e5 來源）。
  - **PHI 提醒：** 核減檔含身分證字號／姓名，比照 D-20/D-21 處理，且 `*.xml` 已全域 gitignore。

### 測試資料

- **D-19（fixture 策略）:** 從真實 `TOTFA.xml` 的 633 筆中抽 3-5 筆代表性案例（涵蓋多醫令、有次診斷、缺 `d10`、單醫令等變化）進版控至 `tests/fixtures/`。

- **D-20（去識別化範圍——使用者明示決定）:** **只置換 `d49` 姓名**。`d3` 病歷號、`d11` 出生年月日、`d19`-`d26` 診斷碼**保留真實值**進版控。
  - **使用者已被明確告知**這三項合併足以在小型診所反推到個人，並在知情下選擇此範圍。
  - **下游 agent 不得自行擴大清洗範圍**——這是經過確認的決定，不是疏漏。

- **D-21（PHI 保護）:** 真實檔 `TOTFA.xml` 含 348 位病患個資，已加入 `.gitignore`（`*.xml` 全域忽略 + `!tests/fixtures/**/*.xml` 例外，讓去識別化 fixture 仍可版控）。符合 D2「病患資料不離開本機」。

### Claude's Discretion

- 三種解析器是否共用統一的回傳基底型別（vs 各自獨立型別）
- 民國年日期轉換：Phase 2 已有 `loaders/dates.py` 的 `parse_flexible_date()`（依字串長度區分 8 碼西元 vs 7 碼民國），規劃階段評估直接重用或抽到共用模組

- dataclass 的確切欄位命名（建議保留 `d3`/`p4` 原始代號作為別名，方便對照規格書除錯）
