<domain>
## Phase Boundary

修正 Phase 9（his-servicing）交付物的三處整合缺陷（milestone audit 2026-08-08 發現）：

1. **W1 狀態機語義**：`/api/appeal/generate` 對剛導入（`imported`）的 appeal 案件直接 `transition(appealed)` 拋 `IllegalTransitionError`（states.py 轉換表僅允許 `imported→{parsed, failed}`）——正常用戶流中 `appealed` 狀態不可達。
2. **W4 契約橋**：`/api/appeal/generate` 回應（`appeal_sections/reason1/reason2/p6_points/total_char_count`）≠ `render_appeal_json` 契約（`sections/word_stats/p1-p9`）——前端無法直接落盤 `appeal_{流水號}.json` 餵給 `build_appeal_xml`/`build_appeal_print`。
3. **W5（本次一併納入）**：`_to_appeal_case` 產出的 CaseStore appeal payload 缺 `case_class`（join key 一半）、`patient_name=None`、無 `orders`——直接作為 submission 餵 `build_appeal_print` 時患者層欄位全留空＋警告、join 無法成立。

不新增能力；僅對齊狀態機語義與契約一致性。`appealed→submitted`（電子上傳後）不屬本次範圍（Phase 10 實機門控）。

</domain>

<decisions>
## Implementation Decisions

### W1 狀態機語義（使用者裁示 2026-08-08）
- **D-01:** `imported→appealed` 合法化——appeal 案件生成申復草稿即視為完成申復（最簡，符合現狀 generate 語義）。保留 `parsed/reviewing/reviewed` 供抽審預審流使用（sampling 案件不受影響；實現時需依 kind 區分或確認轉換表語義不互相污染）。
- **D-02:** `appealed→submitted` 不處理——deferred 至 Phase 10（VPN/實機門控，電子上傳後狀態）。
- 承襲 09-CONTEXT 既有裁示：非法轉換必須拋例外不得靜默允許（P1-1/P0-2/P1-3 同源原則）；轉換歷史（`case_transitions`）保留。

### W4 契約橋（使用者裁示 2026-08-08）
- **D-03:** `/api/appeal/generate` 端點改回 **`render_appeal_json` 標準契約**（`sections/word_stats/p1-p9/...`，見 appeal.py:482-515）——單一契約，前端拿到即可直接落盤 `appeal_{流水號}.json`；不做獨立轉換函數、不做雙契約兼容。
- **D-04:** 前端 `static/index.html` 的 generate 消費**本次一併適配**（改渲染標準契約欄位），測試同步。

### W5 CaseStore→submission 契約（使用者裁示 2026-08-08）
- **D-05:** 建立 CaseStore appeal payload → submission dict 的**標準轉換**（補 `case_class`、`patient_name`、`orders` 等欄位；來源為案件既有資料，缺欄誠實留空＋warning，不捏造——承襲 11-01 誠實降級原則），使落盤的 appeal_json＋submission 可直接餵 `build_appeal_print`。

### Claude's Discretion
- 狀態機轉換表實作形式（依 kind 分表 vs 單表擴充合法邊）
- submission 轉換函數的放置位置與命名（generators 層 vs server 層 helper）
- 前端 index.html 的具體渲染改法（保持既有版面風格）
- 測試組織（沿用 test_server_case_store_integration.py / test_appeal_print.py 慣例）

</decisions>
