## Summary

本次重跑聚焦於安全（CSP、XSS、路徑穿越、LAN 信任、跨站）與月報／EMR 打包路徑的正確性。

已驗證無誤的部分：`lan_trust.is_allowed_host` 的 Host 解析（含 IPv6 括號格式）、`is_cross_site_request` 與 `is_cross_site_read` 的判定順序、`security.py` 的 CSP 套用範圍、`rules.py` 的檔名驗證（`rule_csv_kind` 拒絕路徑成分）、`monthly.py` 的上傳批次名（僅接受 `MONTHLY-\d{6}` 與機構代碼，不會逃逸目錄）、`case_store/monthly.py` 的 case_id（SHA-256 十六進位）、`report_renderer.py` 與 `monthly_report_html.py` 的 HTML 轉義（經檢視，動態值皆經 `escape`）。

### CR-01: `POST /api/emr/batch-package` 的 `facility_code` 未驗證，造成任意路徑寫檔

**File:** `src/elc_audit_engine/api/routes/emr_packaging.py:48` 與 `:160-161`（寫檔）；`src/elc_audit_engine/packagers/emr_batch_packager.py:288` 與 `:295`（`generate_zip_name`）
**Severity:** Critical（安全：任意檔案寫入）
**Issue:** `facility_code = str(body.get("facility_code") or "3503250461").strip()` 直接進入 `generate_zip_name()`，回傳 `f"{fac}_{date_str}_{seq:03d}.zip"`，路由再執行 `file_path = out_dir / zip_name; file_path.write_bytes(zip_bytes)`。`facility_code` 沒有任何格式檢查（應為 10 碼數字），因此可含 `../` 或以 `/` 開頭。已用 `python3 -I` 實測：
- `out_dir / "../../../x_1151118_001.zip"` 解析到 `out_dir` 之外。
- `out_dir / "/tmp/evil_1151118_001.zip"` 因 `pathlib` 的絕對路徑語意，直接取代整個 `out_dir`。

同一模組已有正確的驗證函式 `build_zip_name()`（`generators/emr_review_bundle.py:60-68`，要求 10 碼數字），但此路由未使用。
**Failure scenario:** 任一 LAN 內的用戶端（信任模式下不需憑證）送出 `{"facility_code": "/home/hsu/.config/autostart/x"}`，伺服器即在該路徑寫入 ZIP 格式內容，檔名結尾為 `_<民國日期>_001.zip`。結合 `target` 與空 DB 時的 DEMO 路徑，攻擊者可控制寫入的時機與內容類型。
**Fix:**
```python

try:

except BundleError as exc:
    raise ApiError(str(exc), status=400)

# 並在寫檔前做防禦性檢查（深度防禦）
target = (out_dir / zip_name).resolve()
if target.parent != out_dir.resolve():
    raise ApiError("不合法的封包檔名", status=400)
file_path = target
```

### CR-03: EMR 批次封包靜默截斷為 1000 案

**File:** `src/elc_audit_engine/monthly_package.py:337`（`store.list_by_batch(batch_id)`）；`src/elc_audit_engine/api/routes/emr_packaging.py:53`（`store.list_all(kind=target, limit=1000)`）；預設值見 `src/elc_audit_engine/case_store/store.py:510-511`
**Severity:** Critical（資料完整性：送審包缺案）
**Issue:** `list_by_batch` 與 `list_all` 的預設 `limit` 為 1000，呼叫端未檢查 `count`，超過時靜默只取前 1000 筆。`build_emr_bundle` 的 docstring 與 `monthly.py:391` 宣告「任一案件失敗 → 422，不產生殘缺檔」，但超量案件並不屬於「失敗」而被略過，因此會產出看似完整、實際缺案的 ZIP。同檔 `monthly_audit.py:635-639` 已正確使用分頁，`api/batch_limits.py:18` 的 `refuse_if_truncated` 也已存在，但 EMR 路徑未採用。
**Failure scenario:** 單一批次 1,200 案，EMR 封包只含前 1000 案，HTTP 200 回傳，操作者不知道 200 案未送審。
**Fix:**
```python
# monthly_package.py：分頁讀取，或在超量時拒絕
total = store.count_by_batch(batch_id)
records = []
offset = 0
while True:
    page = store.list_by_batch(batch_id, limit=1000, offset=offset)
    if not page:
        break
    records.extend(page)
    offset += len(page)
if len(records) != total:
    raise BundleError(f"批次共 {total} 筆，讀取 {len(records)} 筆，拒絕產出不完整封包")
```

### WR-08: 院所設定寫入不驗證機構代碼格式與必填條件

**File:** `src/elc_audit_engine/api/routes/misc.py:74-95`（`update_facility`），特別是 `:89`（`if payload.get("source") == "web" or "email" in payload:`）

### WR-09: 代理端在 HIS 寫入成功後仍回報 FAILED，無補償機制
