<objective>
建立**案件狀態機＋SQLite 持久化**，取代目前 `data/uploads/*.json`
的無狀態落盤。狀態集合為 `imported → parsed → reviewing → reviewed →
appealed → submitted`，另有 `failed` 旁支。任務佇列採**同步版**——
狀態欄位即佇列，以「查詢處於某狀態的案件」實現，不引入 Celery／Redis。

Purpose: 目前案件只有一份 JSON 快照，無法回答「這個案件走到哪一步」、
「誰在什麼時候把它推進的」。申復流程需要可追溯性。同時延續本專案核心
原則：**非法轉換必須拋例外，不得靜默產生看似正常的結果**。

Output: 獨立的 `case_store` 子套件（純資料層，不含任何 Flask 依賴），
兩張 SQLite 表（`cases`／`case_transitions`），與兩個測試檔。

**本 plan 刻意不動 `server.py`** —— 端點接線與 `data/uploads/*.json`
遷移由 09-03 處理，讓本 plan 可與 09-01（認證）並行執行。
</objective>

1. 六個主線狀態常數（字串值即持久化值，**不可日後改動**，加註解說明）：
   `STATE_IMPORTED = "imported"`、`STATE_PARSED = "parsed"`、
   `STATE_REVIEWING = "reviewing"`、`STATE_REVIEWED = "reviewed"`、
   `STATE_APPEALED = "appealed"`、`STATE_SUBMITTED = "submitted"`；
   旁支 `STATE_FAILED = "failed"`。
   `ALL_STATES: frozenset[str]` 含全部七個。

2. 顯式轉換表（採**顯式轉換表**而非列舉方法，理由寫入註解：
   轉換表可被測試直接遍歷，新增狀態時漏掉的邊會被測試抓到）：
   `_TRANSITIONS: dict[str, frozenset[str]]`，內容為
   - `imported` → `{parsed, failed}`
   - `parsed` → `{reviewing, failed}`
   - `reviewing` → `{reviewed, failed}`
   - `reviewed` → `{appealed, failed}`（reviewed 為預審終點；申復流程續行）
   - `appealed` → `{submitted, failed}`
   - `submitted` → `frozenset()`（終態，**不可再轉出**，含不可回 imported）
   - `failed` → `{imported, parsed, reviewing, reviewed, appealed}`
     （允許人工排除故障後重試回到失敗前的階段；**不含 submitted**——
      已上傳不可由 failed 直接宣告完成）

3. `class IllegalTransitionError(ValueError)`：屬性 `from_state`／`to_state`；
   訊息格式 `f"非法狀態轉換：{from_state} → {to_state}（允許：{sorted(allowed)}）"`。
   `class UnknownStateError(ValueError)`：狀態值不在 `ALL_STATES`。

4. `def allowed_targets(from_state: str) -> frozenset[str]`：
   `from_state` 不在 `ALL_STATES` → 拋 `UnknownStateError`；否則回轉換表值。

5. `def can_transition(from_state: str, to_state: str) -> bool`：
   兩端狀態未知一律拋 `UnknownStateError`（**不得回 False**——未知狀態
   是系統故障，回 False 會讓它偽裝成「業務上不允許」，正是本專案反覆
   踩到的坑）。

6. `def assert_transition_allowed(from_state: str, to_state: str) -> None`：
   `can_transition` 為 False 時拋 `IllegalTransitionError`。

7. `def requires_reason(to_state: str) -> bool`：僅 `to_state == STATE_FAILED`
   回 True——轉入 failed 必須附失敗原因（見 Task 2 強制）。

建立 `src/elc_audit_engine/case_store/db.py`（沿用 rule_repository/db.py 寫法）：

1. `SCHEMA_CASES` 常數：
   `CREATE TABLE IF NOT EXISTS cases (case_id TEXT PRIMARY KEY, kind TEXT NOT NULL,
   state TEXT NOT NULL, case_seq TEXT, order_code TEXT, payload_json TEXT,
   created_at TEXT NOT NULL, updated_at TEXT NOT NULL, failure_reason TEXT)`
   欄位說明寫入註解：
   - `kind`：`"sampling"`（抽樣預審）或 `"appeal"`（核減申復），
     對應 pipeline 兩個入口
   - `payload_json`：案件資料原樣 JSON（含 PHI；故 DB 檔入 .gitignore）
   - `failure_reason`：**只在 state='failed' 時有值**；與業務結論
     （`payload_json` 內的 `support_level` 等）分屬不同欄位，
     不可用同一欄表達「系統失敗」與「判定裸奔」（P1-1 教訓）

2. `SCHEMA_TRANSITIONS` 常數：
   `CREATE TABLE IF NOT EXISTS case_transitions (id INTEGER PRIMARY KEY AUTOINCREMENT,
   case_id TEXT NOT NULL, from_state TEXT, to_state TEXT NOT NULL,
   reason TEXT, actor TEXT, created_at TEXT NOT NULL)`
   `from_state` 為 NULL 代表建案（初始寫入 imported）。
   `actor` 記錄推進者識別（09-03 會傳入 `g.caller_id`；**不記 PHI**）。

3. `SCHEMA_INDEXES`：
   `CREATE INDEX IF NOT EXISTS idx_cases_state_kind ON cases (state, kind)`
   （同步佇列的主查詢路徑）、
   `CREATE INDEX IF NOT EXISTS idx_transitions_case ON case_transitions (case_id, id)`

4. `def get_connection(db_path: str) -> sqlite3.Connection`：
   `os.makedirs(os.path.dirname(db_path), exist_ok=True)`；
   連線後 `conn.row_factory = sqlite3.Row`；
   執行 `PRAGMA foreign_keys = ON`。

5. `def init_schema(db_path: str) -> None`：建兩表與兩索引（冪等）。

6. `_ALLOWED_TABLES = {"cases", "case_transitions"}`——與 rule_repository
   同慣例，SQL 表名一律寫死於靜態語句，不動態組裝。

建立 `src/elc_audit_engine/case_store/store.py`：

1. `@dataclass(frozen=True) class CaseRecord`：欄位對應 cases 表
   （`case_id`／`kind`／`state`／`case_seq`／`order_code`／`payload`（dict）／
   `created_at`／`updated_at`／`failure_reason`）。
   `@dataclass(frozen=True) class TransitionRecord`：`case_id`／`from_state`／
   `to_state`／`reason`／`actor`／`created_at`。

2. 例外類（**與使用處同模組定義，避免 handler 引用未定義類的 NameError**）：
   `class CaseStoreError(Exception)`（基底）、
   `class DuplicateCaseError(CaseStoreError)`、
   `class CaseNotFoundError(CaseStoreError)`、
   `class MissingFailureReasonError(CaseStoreError)`。

3. `class CaseStore`：`__init__(self, db_path: str | None = None)`，
   None 時用 `config.settings.CASES_DB_PATH`；建構時呼叫 `init_schema`。
   方法：

   - `create(self, *, case_id: str, kind: str, case_seq: str | None = None,
     order_code: str | None = None, payload: dict | None = None,
     actor: str | None = None) -> CaseRecord`
     - `case_id` 先過 `safe_filename(case_id, "case_id")`（校驗後拒絕；
       case_id 會出現在日誌與後續檔名，不得含路徑成分）
     - `kind` 須為 `"sampling"` 或 `"appeal"`，否則拋 `CaseStoreError`
     - 初始 state 固定 `STATE_IMPORTED`
     - 已存在同 case_id → 拋 `DuplicateCaseError`（**不得覆寫**——
       覆寫會抹掉既有狀態與轉換歷史，等於靜默丟失可追溯性）
     - 同一交易內寫 cases 一列 ＋ case_transitions 一列
       （`from_state=None, to_state='imported', actor=actor`）
     - 時間戳一律 `datetime.now(timezone.utc).isoformat()`

   - `get(self, case_id: str) -> CaseRecord`：不存在拋 `CaseNotFoundError`
     （**不回 None**——None 會讓「查無案件」與「案件存在但無資料」混淆）

   - `transition(self, case_id: str, to_state: str, *, reason: str | None = None,
     actor: str | None = None) -> CaseRecord`
     - 先 `get` 取現行狀態（不存在拋 `CaseNotFoundError`）
     - 呼叫 `states.assert_transition_allowed(current, to_state)`
       （非法即拋 `IllegalTransitionError`，**不吞不降級**）
     - `states.requires_reason(to_state)` 為 True 且 `reason` 空白 →
       拋 `MissingFailureReasonError`（轉入 failed 必須說明原因）
     - **單一 SQLite 交易**內：`UPDATE cases SET state=?, updated_at=?,
       failure_reason=?` （非 failed 時 failure_reason 寫回 NULL，
       避免舊失敗原因黏在成功狀態上）＋ `INSERT INTO case_transitions`
       一列。以 `with conn:` 確保原子性——狀態與歷史不可只寫一邊
     - 回傳更新後的 `CaseRecord`

   - `history(self, case_id: str) -> tuple[TransitionRecord, ...]`：
     依 `id` 升冪回傳；案件不存在拋 `CaseNotFoundError`

   - `list_by_state(self, state: str, *, kind: str | None = None,
     limit: int = 100) -> tuple[CaseRecord, ...]`：
     **這就是同步版任務佇列的取件介面**（狀態欄位即佇列）。
     `state` 不在 `ALL_STATES` → 拋 `UnknownStateError`。
     依 `created_at` 升冪（FIFO）。docstring 明寫：目前為同步取件，
     呼叫端自行處理；不引入 Celery／Redis（CONTEXT 決策，單機部署）

   - `list_all(self, *, kind: str | None = None, limit: int = 1000)
     -> tuple[CaseRecord, ...]`：供 GET 案例清單端點（09-03）使用

   - `counts_by_state(self, *, kind: str | None = None) -> dict[str, int]`：
     `SELECT state, COUNT(*) ... GROUP BY state`，供佇列深度觀測
