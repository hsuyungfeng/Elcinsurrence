# Phase 31 可行性研究：櫃台「健保醫療資訊雲端查詢系統」病歷擷取技術評估

**版本**：1.0  
**日期**：2026-11-12  
**依據需求**：D-31-34、D-31-35、D-31-36  
**階段定位**：可行性研究筆記（Spike Note）。**本計畫不新增、不修改任何系統程式碼（D-31-35）**。

---

## 1. 背景與問題定義

- **情境描述（D-31-34）**：櫃台工作站主要職責為病人掛號、插健保卡過卡驗身，並透過健保署「健保醫療資訊雲端查詢系統」（NHI MediCloud 2.0，俗稱健保雲端病歷）預先讀取病患過往用藥、檢驗檢查報告及跨院所就醫紀錄。
- **核心目標**：評估在櫃台人員查詢雲端病歷時，同步擷取讀取內容或產生結構化摘要之技術可行性與法規邊界。
- **核心約束（D-31-36）**：櫃台雲端病歷擷取屬於輔助或附加作業，**絕對不得阻塞診間核心看診主流程**（包括語音錄音、分段上傳、SOAP 生成、醫師審核與 HIS 回寫）。

## 2. 候選技術方案詳細評估

本節依據計畫要求評估五種方案，並以 `[VERIFIED]`（已查證事實）、`[CITED: 來源]`（有官方/法規來源引用）、`[ASSUMED]`（工程推測或待院所確認項目）進行標註。

### 方案 (a)：健保署官方 Web 服務介面 / NHI MediCloud 專用 API

- **運作方式**：
  直接呼叫健保署提供之「健保醫療資訊雲端查詢系統 API」或介接 HIS 廠商內建之雲端查詢模組，以結構化 JSON/XML 取得用藥與檢驗資料。
- **權限與憑證需求**：
  - [CITED: 健保署醫療資訊雲端查詢系統作業要點] 必須透過健保專線 VPN（IPSec VPN）或院所固定實體網路連線。
  - 必須同時插掛：(1) 醫事機構卡／醫事人員卡、(2) 病患本人健保 IC 卡（或虛擬健保卡同意授權憑證），並經健保 SAM（安全模組）金鑰簽章認證。
- **對健保端／瀏覽器變更**：
  無須修改瀏覽器，但院所端須向健保署申請 API 介接授權或啟用 HIS 廠商的加值介接模組。
- **對診間主流程影響**：
  零影響。若採獨立背景服務輪詢或掛鉤 HIS 櫃台事件，完全與診間快捷列隔離。
- **隱私與法規疑點**：
  - [CITED: 個人資料保護法第6條特種個資規範] 醫療與健康檢查資料屬於特種個資，查詢與保存須有特定法定目的及病患授權。
  - [ASSUMED] 健保署介接條款明定雲端查詢資料僅限當次診療醫療目的使用，若私自匯出保存於非申報核銷之第三方系統，可能涉及違規。
- **「僅記錄讀取事件與摘要而不保存全文」變體**：
  高度可行。僅記錄「已讀取雲端藥歷」事件（含時間、查詢項目代碼、異常警示標籤如重複用藥），不保存完整病歷全文，大幅降低法規衝擊。
- **綜合狀態標註**：
  - 健保卡與醫事卡雙卡認證機制：`[VERIFIED]`
  - 官方現行提供 HIS 整合 API 方案：`[CITED: 健保署醫事機構雲端系統整合規範]`
  - 本專案取得正式授權時程與成本：`[ASSUMED]`（需依診所與 HIS 廠商合約決定）。

### 方案 (b)：以 agent-desktop / Windows UI Automation (UIA) 讀取畫面文字

- **運作方式**：
  櫃台開啟健保雲端查詢獨立用戶端程式（如健保署專用 VPN 查詢用戶端）或 HIS 內嵌視窗時，地端背景透過 `agent-desktop` 的 UIA 樹狀遍歷，抓取 `Table`、`ListItem`、`Edit` 等文字控制項內容。
- **權限與憑證需求**：
  - Windows 本地標準使用者權限即可操作 UIA。
  - 健保卡與醫事人員卡驗證已由前景操作人員在官版軟體完成，UIA 不直接處理憑證。
- **對健保端／瀏覽器變更**：
  零變更。不需修改官方軟體或安裝瀏覽器外掛。
- **對診間主流程影響**：
  若由地端獨立程序執行，不佔用診間 HTTP 通道；但若 UIA 掃描佔用大量 CPU 或頻繁抓取 snapshot，可能造成地端電腦短暫卡頓。
- **隱私與法規疑點**：
  - 螢幕自動爬蟲（Screen Scraping）可能抓取到畫面上的病患身分證號、姓名、跨院敏感就醫科別（如身心科、傳染病）。
  - 若寫入未去識別化日誌，直接違反 `AGENTs.md` 的 PHI 不變式。
- **「僅記錄讀取事件與摘要而不保存全文」變體**：
  可行。UIA 只偵測視窗標題出現「雲端查詢成功」或抓取重複用藥紅字標記，回報「雲端已查驗」，不抓取明細表格。
- **綜合狀態標註**：
  - Windows UIA 讀取視窗能力：`[VERIFIED]`（已在 Phase 30-09 實測）
  - 官方查詢軟體控制項是否均向 UIA 暴露：`[ASSUMED]`（部分舊版以 Delphi/ActiveX 撰寫，控制項可能為無障礙不可見）。

### 方案 (c)：瀏覽器擴充套件讀取頁面 DOM（WebBrain Bridge 模式）

- **運作方式**：
  健保雲端查詢系統若以 Chrome/Edge 瀏覽器開啟（https://medcloud.nhi.gov.tw/），透過專屬 Browser Extension（或既有 WebBrain Chrome 插件）監聽 DOM 渲染，於資料表格載入完成時抽取藥品代碼、檢驗項目並經由本機 WebSocket / HTTP 傳遞。
- **權限與憑證需求**：
  - 瀏覽器擴充套件安裝權限（可於 Edge/Chrome 以開發者模式或群組原則派發）。
  - 人員登入與健保卡檢核仍在官方 Web 頁面完成。
- **對健保端／瀏覽器變更**：
  需在櫃台電腦的瀏覽器中安裝擴充外掛。若健保雲端系統更新 DOM 結構，擴充套件需同步維護。
- **對診間主流程影響**：
  零影響。外掛與 ElcServer 之間透過獨立 API 端點非同步通訊，完全不與快捷列或 SoapVoice 流程共用佇列。
- **隱私與法規疑點**：
  - 擴充套件具有網頁讀取權限，需實施白名單鎖定 `medcloud.nhi.gov.tw`，避免抓取其他網頁資料。
  - 需實施嚴格 CSP 與本機 Token 驗證，防止惡意腳本串改。
- **「僅記錄讀取事件與摘要而不保存全文」變體**：
  極度容易實作。DOM 解析器可直接只挑選「檢驗檢查異常項目」或「重複用藥列表」轉為簡要代碼與標籤，不提取完整歷史清單。
- **綜合狀態標註**：
  - WebBrain DOM 抽取結構：`[VERIFIED]`（`webbrain_bridge.py` 內已有 `NHI_CLOUD_SCHEMA` 定義）
  - 櫃台人員是否統一使用瀏覽器版（而非 HIS 專屬嵌入視窗）：`[ASSUMED]`（視診所作業習慣而定）。

### 方案 (d)：畫面截圖加本機 OCR

- **運作方式**：
  定時或由櫃台快捷鍵觸發視窗截圖，利用 Windows Media OCR API 或本機輕量模型（如 Tesseract）辨識雲端藥歷與檢驗文字。
- **權限與憑證需求**：
  - Windows 本機桌面截圖權限。
- **對健保端／瀏覽器變更**：
  完全無侵入性，零變更。
- **對診間主流程影響**：
  OCR 運算耗用 CPU/GPU 資源較大；若在低階櫃台電腦上執行可能導致其他應用程式延遲。
- **隱私與法規疑點**：
  - 截圖包含完整螢幕畫面（易錄入無關個資或背景視窗）。
  - 暫存圖檔落地若未立即銷毀，有外洩風險。
- **「僅記錄讀取事件與摘要而不保存全文」變體**：
  不易精確控制，OCR 輸出文字仍需進行 NLP 關鍵字匹配，成本最高且最不穩定。
- **綜合狀態標註**：
  - OCR 本機推論可行性：`[VERIFIED]`
  - 繁體中文醫療詞彙與藥名辨識正確率及維護成本：`[ASSUMED]`（誤字率高，不建議用於醫療流程）。

### 方案 (e)：櫃台人員手動複製貼上至快捷列

- **運作方式**：
  快捷列提供一小型文字框或快捷按鈕，由櫃台人員選取雲端查詢文字後複製，在快捷列按貼上。
- **權限與憑證需求**：
  無需額外系統權限，完全依賴人工操作。
- **對健保端／瀏覽器變更**：
  零變更。
- **對診間主流程影響**：
  零技術影響，但干擾櫃台人員既有作業動線，增加櫃台負擔。
- **隱私與法規疑點**：
  最低。操作均由人員明確認可與手動傳送。
- **綜合狀態標註**：
  - 人工作業易遭櫃台人員抗拒或遺漏：`[VERIFIED]`（臨床人因工程普遍規律）。

## 4. 診間主流程隔離架構設計（防護 D-31-36）

若未來使用者決定將櫃台雲端病歷擷取功能排入實作，必須遵循下列架構防護原則：

1. **獨立通訊端點（Dedicated Endpoint）**：
   - 櫃台資料僅透過獨立 API 端點傳輸（例如 `POST /api/counter/cloud-records`），不得重用或干擾 `POST /api/cycles`、`POST /api/cycles/{id}/chunks` 或 `POST /api/cycles/{id}/confirm`。
2. **獨立佇列與儲存（Separate Storage/Queue）**：
   - 櫃台雲端紀錄寫入獨立資料表（如 `counter_cloud_events`），不與 `cases` 或 `soap_drafts` 混用，其失敗不觸發診間循環中斷。
3. **無鎖與非阻塞（Non-blocking & Best-effort）**：
   - 櫃台端資料傳輸採非同步與最大努力送達（Best-effort）模式；若連線失敗或伺服器逾時，僅在本機標記重試或警告，絕不阻擋診間醫師的 SOAP 確認視窗或 HIS 回寫。
4. **脫敏與最小化（Data Minimization）**：
   - 僅萃取與當次診療相關之特定欄位（如近期血糖/血壓數據、近 30 天重複藥品清單），病患身分識別僅保留病歷號（`patient_ref`）或當次掛號序號，不得跨網段明文傳輸姓名與身分證號。

## 5. ## 結論與建議

### 建議策略
1. **短期策略（本 Phase 31）**：
   - **維持原決定，本 Phase 31 暫不實作櫃台雲端病歷擷取功能**。
   - Phase 31 應全神貫注於交付診間快捷列（紅綠黃燈）、SoapVoice 串流分段落地與多連線監控三項核心資產。
2. **中長期策略（後續獨立 Phase）**：
   - **首選方案**：若院所櫃台主要透過瀏覽器操作健保雲端查詢，以 **方案 (c) 瀏覽器擴充套件（WebBrain Bridge 模式）** 為最佳實作路徑，開發成本最低且與現有架構相容性最高。
   - **次選方案**：若院所櫃台使用 HIS 廠商專用查詢視窗，則以 **方案 (b) agent-desktop UIA 讀取** 搭配嚴格欄位白名單實作。

### 前置確認事項清單（需使用者／診所方確認）
- [ ] **確認櫃台實際操作介面**：櫃台人員查詢雲端病歷時，是使用 Chrome/Edge 瀏覽器開啟 Web 網頁，還是點擊 HIS 內部內嵌按鈕跳出視窗？
- [ ] **確認資訊保存範圍**：診所是否僅需「重複用藥警示與三高檢驗摘要」，抑或是需要留存完整用藥歷史？（強烈建議採最小化摘要，避免觸犯個資法特種個資過度蒐集）。
- [ ] **確認 HIS 廠商現有能力**：詢問診所 HIS 原廠（如展望或耀聖）是否有提供櫃台「一鍵匯入雲端藥歷至 HIS 本地資料庫」之功能；若 HIS 已具備此功能，本系統可直接由 HIS 本地資料庫讀取，無須自行爬取雲端系統。
