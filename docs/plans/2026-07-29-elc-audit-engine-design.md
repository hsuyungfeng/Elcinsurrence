> 定稿日期：2026-07-29

## 1. 專案定位

**檔案進、檔案出的本地引擎**（Phase 1），未來包成 doctor-toolbox HIS 模組（Phase 2）。病歷資料全程不離開本機。

兩大功能共用同一條比對管線，僅輸出不同：

- **病歷補強**（送審前防守）：抽審案件 → 比對醫令與病歷 → 指出支持度缺口 → 生成候選補強敘述供醫師點選
- **申復生成**（核減後救援）：核減清單 → 對每筆核減醫令 → 生成 p8/p9 申復理由草稿（≤2000 中文字）＋申復 XML 欄位

## 2. 系統架構

```text
   輸入層                     共用比對引擎 (Core)                  輸出層
─────────────      ┌──────────────────────────────────┐    ─────────────
申報XML(抽審案件)──►│ ① 解析器: XML/核減檔/SOAP          │──► 病歷補強報告.md
核減清單檔      ──►│ ② 病歷彙整器: 近半年雲端病歷整合     │    · 醫令支持度缺口
                   │    (就診紀錄/檢驗/檢查/影像清單)     │    · 半年病史摘要
雲端病歷(半年) ──►│ ③ 規則庫: PageIndex+預編譯快取      │    · 候選補強敘述(逐條點選)
  Provider介面     │    +支付規定SQLite+ChromaDB輔助     │
                   │ ④ 比對器: 醫令↔規則↔病歷 三方比對   │──► 申復理由草稿
過去申復案例    ──►│ ⑤ 生成器: llama.cpp :8080          │    p8/p9 ≤2000字
                   └──────────────────────────────────┘    +申復XML欄位
```

**技術棧**（沿用 `~/Desktop/DrtoolboxLocalServer`）：Python + uv、Flask（Phase 2）、python-docx、pandas、pageindex、SQLite、ChromaDB（輔助）。

**LLM**：llama.cpp server（localhost:8080，OpenAI 相容 API），Ornith-1.0-9B Q6_K_XL，n_ctx 32768。設定沿用 `config/llama_config.json` 模式。

**病歷彙整器**：透過 Provider 介面拉取病患近半年就診紀錄、檢驗報告、檢查結果、影像清單，彙整為「病史時間軸」。Phase 1 用本地檔案 Provider；Phase 2 接 doctor-toolbox（`his_connection.py` 唯讀 SQLite / `cloud_sync_service.py` 模式）。

## 3. 規則庫（三層）

### 3.1 結構化層（SQLite，精準比對，零幻覺）
- `payment_rules` ← `醫療服務給付項目251027準確板_已優化填入支付規定.csv`（醫令代碼→支付規定/點數/科別限制）
- `drug_rules` ← `藥品項查詢項目檔260605.csv`（藥品代碼→適應症/給付條件）

### 3.2 條文層（PageIndex 為主）
- 語料：`officialdocument/審查注意事項/` 全部 .doc/.docx（各科別＋總則＋部/章/節條文）
- PageIndex 樹狀索引保留條文層級（chunk 切割會破壞上下文；醫令代碼對嵌入向量無區辨力）
- **`rule_mapping` 預編譯快取**：離線以 PageIndex 導航建 (醫令代碼, 科別, 文件版本) → [條文位置, 條文全文] 對照表，存 SQLite。線上查詢零 LLM 呼叫；查不到的罕見醫令即時導航後回寫快取。規則文件更新時重跑（與 DrtoolBox `/medicalorderupdate` 流程銜接）

### 3.3 輔助層（ChromaDB）
- 無代碼可查的自由文字場景：類似申復案例檢索、跨文件模糊查詢
- 檢索時以就醫科別（d8）過濾 metadata

## 4. 三方比對器（引擎核心）

**步驟 1 — 要求萃取**（離線已編譯）：從 `rule_mapping`＋`payment_rules` 取該醫令審查要求，正規化為檢核項清單（類型：適應症/頻率限制/病歷記載要求…，各附規則出處）。

**步驟 2 — 證據搜尋**：對每個檢核項，從「當次 SOAP」（soap-classifier 邏輯移植為 Python，S/O/A/P 分段定位）與「半年病史時間軸」找證據。LLM 收到「檢核項＋病歷段落」只回答 `支持/部分支持/無記載`＋引用原文句子 — **逐項小問題，LLM 是判定者不是回憶者**（9B 模型答小題可靠，寫大論文不可靠）。

**步驟 3 — 匯總判定＋候選補強生成**：

```text
每筆醫令 → 支持度分級：
  ✅ 充分 → 直接通過，列證據出處
  ⚠️ 薄弱 ┐
  ❌ 裸奔 ┴→ 對每個缺口，LLM 生成 1~3 條「候選補強敘述」
            └ 醫師逐條：[採用] [編輯後採用] [略過] [標記不符事實]
```

候選敘述約束（合規關鍵）：
1. **只能基於既有線索擴寫**（半年病史、當次 SOAP、規則要求的記載格式）
2. **無線索時生成提示型候選**（「若實際有執行，請補充：…」），事實補充留給醫師
3. **每條附規則出處**

## 5. 醫師審核流程（逐條審＋整稿確認）

```text
比對器缺口 → 候選補強敘述（逐條）
   │  醫師逐條：[採用] [編輯後採用] [略過] [標記不符事實]
   ▼
採用清單 → 組裝器 → 完整草稿（p8/p9 四段結構）
   │  醫師整稿：自由刪改 → 最終確認
   ▼
定稿 + 審核軌跡 JSON（每條狀態、原文、編輯後文、時間）
```

- 逐條審 = 合規責任歸屬（AI 建議與醫師確認界線清楚）＋低認知負擔＋採用率數據飛輪
- 整稿確認 = 文氣銜接、重複、邏輯順序只有整體看得出
- 「標記不符事實」= 幻覺/病史誤讀回饋，獨立記錄，品質監控核心指標
- Phase 1：Markdown checkbox 檢核表，醫師勾選/編輯後存檔，組裝器讀取生成整稿；Phase 2：HIS 點選 UI，同一套狀態機

## 6. 申復理由生成（p8/p9）

**組裝式四段結構**（審查醫師習慣的論述順序）：

```text
p8/p9 = ① 案情摘要    病患○歲，主診斷(d19)，就醫日期，核減醫令與核減理由
        ② 醫療必要性  半年病史時間軸：相關診斷/檢驗趨勢/前次治療反應
        ③ 規則依據    支付規定與審查注意事項條文原文（rule_mapping 直接帶入）
        ④ 病歷佐證    SOAP 原文句子（比對器標記「有證據」項）＋醫師採用的補強敘述
```

- 每段分開生成（小任務原則），素材全來自比對器結果 — LLM 是文字組織者不是事實來源
- 字數控制器：>2000 字按 ④引文摘短 → ②病史壓縮 裁剪；①③ 為骨架不動
- 每筆核減醫令獨立生成（審查逐醫令判定）
- 產出 XML 欄位：p8/p9、P4/P5（訴求成數/數量）、**P6 不申覆強制填 0（程式硬檢查）**、p7（新事證附件填 Y）
- 輸出：`申復草稿_{案件流水號}.md`（醫師審閱版）＋ `appeal_{流水號}.json`（Phase 2 轉申復 XML）

## 7. 錯誤處理

| 故障點 | 處理 |
|---|---|
| llama.cpp :8080 未啟動/逾時 | 啟動健康檢查；逾時 60s 重試 2 次 → 該檢核項標「待人工」，不阻斷整案，報告末列未完成清單 |
| LLM 回傳格式跑掉 | 判定任務強制 JSON schema＋解析失敗換措辭重試 → 仍失敗降級「待人工」 |
| 申報 XML 欄位缺漏 | 致命（無 d1/d3 → 整案拒收）vs 可容忍（缺 d10 → 警告繼續） |
| 規則庫查無醫令 | 入「未知醫令」清單 → 即時 PageIndex 導航 → 仍無 → 標「查無規則依據，建議人工查核」 |
| 病史 Provider 不可用 | 降級：只用當次 SOAP，報告開頭標「⚠ 本報告未含病史佐證」 |

**硬性檢查（pure function，不走 LLM）**：P6 填 0、2000 字上限、檔名編碼（2+1+2+6 碼）、申復 XML 必填欄位。

## 8. 測試策略

1. **單元測試**：解析器（電子抽審.md 內真實 XML 範例當 fixture）、字數裁剪、硬性檢查
2. **規則庫驗收**：抽 20 個常見醫令（01015C、64140C…）人工核對 rule_mapping 正確率
3. **LLM 判定評測**：30 組「檢核項×病歷段落」金標準（支持/部分/無記載）通過率 — 換模型時的回歸基準
4. **端到端**:規格造 3 個完整案例（充分/薄弱/裸奔各一）
5. **真實樣本回放**：真實核減案與過去人工申復比對品質
